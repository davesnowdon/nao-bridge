# Project decisions

- The replacement API has no v1, FluentNao, or existing application compatibility requirement. FluentNao is inspiration, not a public contract. Prefer a small, coherent API for common robot tasks over exposing every NAOqi method.
- Events use SSE without historical replay in the first contract; reconnect reports a gap and fresh state. Commands use HTTP. No required MQTT or extra container.
- The language-neutral HTTP/SSE contract is authoritative; Python is its first client. Keep robot semantics/defaults on the server and document client lifecycle behavior independently of Python. Future Rust/other clients are design considerations, not implementation scope for the four increments.
- Use a thin Python 2 NAOqi agent and a modern API process in one container. Use modern Python/ASGI on maintained Ubuntu 24.04 with a private, pinned Python 2/SDK bundle; the Linux packaging comparison passed. Keep library paths process-local and use the base glibc. Rust is a fallback, not a prerequisite for future Rust clients. See [docs/runtime-design.md](docs/runtime-design.md).
- Linux amd64 packaging/IPC evidence and the selected recipe are in [docs/inverted-packaging-experiment.md](docs/inverted-packaging-experiment.md), with a reproducible robot-free harness. Production increment-1 evidence is in [docs/implementation-status.md](docs/implementation-status.md); neither loopback suite proves physical stop behavior. Keep hardware/platform gates explicit.
- Ubuntu's packaged Flask was intentional because legacy dependencies were unavailable from PyPI. Preserve the working SDK environment during the split; this does not require retaining Flask once the modern process owns HTTP.
- Retain recordings/assets and server-side sequences, including parallel execution and child cancellation. Explicit advance session reservations and event replay are deferred; command ownership and sequence reservations remain required.
- The target design and four delivery increments are in [docs/api-plan.md](docs/api-plan.md) and [docs/delivery-plan.md](docs/delivery-plan.md). The full plans include later increments; use the canonical schemas and implementation-status document to distinguish delivered behavior.
- Use modern Recorder and Wanderer applications, plus a scripted presentation, as acceptance cases. Keep their UI, editing, mapping, and planning logic outside the bridge.
- Research evidence and unresolved hardware questions are in [docs/research-notes.md](docs/research-notes.md). Distinguish reproduced software defects from unverified hardware behavior.

- Use uv for project runtimes/dependencies; do not depend on a developer’s pyenv setup. The API process must never inherit the agent’s legacy library paths.
- Software work through 1C is authorized before physical robot and Apple Silicon acceptance. Keep `hardware_verified: false`; do not advertise motion/hold safety on the strength of fake or loopback tests.

- New applications must work without bridge reconfiguration: allow browser origins by default with CORS support; do not add a per-app allowlist. The container runs without client credentials or a data volume. Sessions, operations, subscriptions, retry keys and resource ownership are process-local; API restart starts empty and never replays commands. Retain agent restart supervision. Future recording assets may require storage, but do not reintroduce persistent operation recovery.
